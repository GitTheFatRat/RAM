# M14.4 HOTFIX: WebView2 login through the account's proxy

Follow docs/prompts/RUNBOOK.md (rules, gates, token budget, security, autonomy). First add M14.4 to docs/STATE.md as pending. Batch file writes; do not narrate. Run the FULL RUNBOOK gates, not only the build.

## PURPOSE AND HONEST LIMITS
The login browser currently uses the machine's direct network while the tool's own API requests can use a per-account proxy. This hotfix lets the user run the login browser through the same proxy and stores that proxy on the new account, so the tool's login and API traffic share one network path.
Limits that must be stated in the UI, README.vi.md and SECURITY.md (and nowhere contradicted):
1. The proxy covers the login browser and the tool's own HTTP requests. The Roblox game client is started through the roblox-player protocol by Windows and connects directly; it does NOT use this proxy. This tool does not make game traffic follow the proxy.
2. Do not claim that a proxy prevents bans, flags, or specific Roblox errors. No such claim is verified.
3. No third-party IP-check or geolocation services anywhere. Only roblox.com hosts are contacted.

## 1. PRE-LOGIN PANEL (LoginWindow)
1. Show a proxy panel before any browser exists: Type (None default, HTTP, SOCKS5), Host, Port, Username, Password (PasswordBox), buttons "Test proxy", "Start browser", "Cancel". None means a direct connection and the other fields may be blank.
2. The WebView2 control must not be in the visual tree and must not initialize until "Start browser" succeeds validation. Create it in code at that moment (no Source set in XAML).
3. Pure validation function in Core, unit tested. AdditionalBrowserArguments is a single string, so unvalidated input could inject extra Chromium flags; validate strictly:
   - Host: letters, digits, '.', '-' (max 253 chars) or an IPv4 or IPv6 literal. No whitespace, control characters, quotes, '/', '\', '@', ';', ',', ':' (except inside an IPv6 literal), '=' or leading '-'.
   - Port: integer 1 to 65535.
   - Username at most 128 characters and Password at most 256 characters, no control characters. Both optional.
   - Invalid input shows a localized inline error and starts nothing.
4. "Test proxy": build an HttpClient through the same ProxyConfig-to-handler code used by the tool's HTTP factory (SocketsHttpHandler.Proxy, UseCookies false, AllowAutoRedirect false, 10 s timeout) and GET https://www.roblox.com/. Show only a localized result (success, HTTP status, or an error category). Send no cookie. Do not display or log the proxy address.

## 2. WEBVIEW2 ENVIRONMENT
1. Pure builder function composes the argument: HTTP gives `--proxy-server=http://{host}:{port}`, SOCKS5 gives `--proxy-server=socks5://{host}:{port}`, IPv6 literals in brackets, None gives no argument. Test exact outputs.
2. Create the environment explicitly: `CoreWebView2Environment.CreateAsync(null, tempUserDataFolder, options)` with `CoreWebView2EnvironmentOptions.AdditionalBrowserArguments` set, then `await webView.EnsureCoreWebView2Async(environment)`. Keep the unique temp profile folder and the existing cleanup (retry delete, startup sweep).
3. On initialization failure show a localized error and return to the panel.

## 3. PROXY AUTHENTICATION
1. Subscribe to CoreWebView2.BasicAuthenticationRequested BEFORE navigating. Use the real API surface: check it in the Microsoft Learn documentation (MCP if available) instead of following this text literally. To the Tech Lead's knowledge the event args expose Uri, Challenge, Response (UserName and Password) and Cancel, and there is NO Handled property, so do not write `args.Response.Handled`. Use a deferral only if the API requires it.
2. Never hand proxy credentials to arbitrary sites. Respond only when the challenge is for the configured proxy (the args Uri host equals the configured proxy host, case-insensitive, or the API explicitly marks a proxy challenge). Otherwise set Cancel to true. Also set Cancel to true when no credentials were supplied. State in the report which condition the API allowed. Implement the decision as a pure function behind a small abstraction of the args so it is unit tested.
3. Memory hygiene: convert the PasswordBox content to a SecretValue immediately and clear the PasswordBox. Call Reveal() ONLY inside the authentication handler at the last moment (a managed string is unavoidable for the WebView2 API and cannot be zeroed; state this in SECURITY.md). Dispose the SecretValue when the login window closes.
4. ArchitectureTests: the Reveal() allowlist grows by EXACTLY ONE entry for the file that contains the handler (for example src/App.Wpf/Services/WebViewProxyAuthHandler.cs). Justify it in the report.
5. Never log host, port, username or password (booleans and counts only).

## 4. NAVIGATION FLOW
1. After the environment initializes: hide the panel, show the WebView2, navigate to https://www.roblox.com/login. Keep: navigation restricted to roblox.com and *.roblox.com, cookie polling, the 10 minute timeout, the loading overlay hidden on NavigationCompleted, and cleanup.
2. If navigation fails (connection or proxy errors), show a localized message with a "Change proxy" button that returns to the panel and disposes the current WebView2 and its profile folder.

## 5. CARRY THE PROXY ONTO THE ACCOUNT
1. LoginWindow returns the captured cookie (SecretValue) and the ProxyConfig used (null for None).
2. When the account is created through "Add via login", store that ProxyConfig on the Account (the password stays a SecretValue inside the encrypted vault, as specified in M10). The immediate validation after login must use that proxy.
3. "Add via cookie" and editing remain unchanged. Do not ask the user to retype the proxy anywhere.
