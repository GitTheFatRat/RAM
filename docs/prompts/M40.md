# UAT & FLOW VERIFICATION PLAN (M38 ARCHITECTURE)

**Target Build:** M38 (Smart Launch Scheduler & Anti-Hyperion Compliance)
**Objective:** Manual verification of core application flows post-refactor. These tests ensure the system operates within safe boundaries (Sanctioned Remediation) and properly handles rate limits without queue corruption.

## FLOW 1: Session Management & Auth Cache Verification

**Goal:** Validate the Persistent Profile setup and the 5-minute authentication cache.

* [ ] **Step 1.1: Browser Initialization:** Click the Incognito/Browser button in the UI.
  * *Expected Result:* The browser opens and routes directly to `https://www.roblox.com/NewLogin#signup`. There should be no blank screen errors or infinite 302 redirects to VNG.

* [ ] **Step 1.2: Persistent Profile & Selective Clearance:** Log into an account successfully. Close the browser. Open the browser again.
  * *Expected Result:* The browser must ask for login credentials (verifying `.ROBLOSECURITY` was cleared). HOWEVER, inspecting the cookies (F12 -> Application -> Cookies) should reveal that trust/device tokens (e.g., `rbx-ip2`, `RBXEventTrackerV2`) are still present and intact.

* [ ] **Step 1.3: Auth Cache (5-Min TTL):** Select 10 accounts and click `Check All` three times in rapid succession.
  * *Expected Result:* Only the first click should result in network latency. The second and third clicks must resolve almost instantly (< 0.1s) as they hit the SHA-256 validation cache. No `429 Too Many Requests` errors should be triggered on the backend.

## FLOW 2: Launch Queue & Circuit Breaker Verification

**Goal:** Verify Jitter delay and the `AuthErrorCodes.RateLimited` backoff (Ensure the "dead queue" bug is resolved).

* [ ] **Step 2.1: Jitter Pacing Enforcement:** Select 3 offline accounts. Click `Launch Selected`.
  * *Expected Result:* Account 1 launches. The UI must then display a countdown timer for Account 2. This timer must equal the base delay (e.g., `20s`) + `[A random Jitter value between 1.5s and 6.0s]`. Account 3 follows the same pattern.

* [ ] **Step 2.2: Rate Limit Circuit Breaker (Crucial Fix):** Force a 429/403 Rate Limit (either by setting launch delay to 0s if allowed, or spamming login requests), then attempt to launch 4 accounts.
  * *Expected Result:* When Account 1 or 2 hits the `429/403` limit, the queue **MUST NOT DIE OR DISAPPEAR**. The system must pause the queue, display a backoff timer (e.g., `30s` or `60s` for the first penalty), and automatically resume launching the remaining accounts once the cooldown expires.

## FLOW 3: Window Management (Auto-Tiling) Verification

**Goal:** Ensure `RobloxWindowSizer` captures and resizes the client without relying on aggressive Win32 hooks.

* [ ] **Step 3.1: Splash Screen Resilience:** Launch an account into a heavy map that utilizes a custom splash/loading screen.
  * *Expected Result:* The window may flicker or resize itself during the 3D scene load. The tool must not abandon the sizing operation during this phase.

* [ ] **Step 3.2: Trailing Enforcement:** Wait for the map to fully load and the character to spawn.
  * *Expected Result:* Within a maximum of **15 seconds** (or 6 polling passes) after the load, the game window must be forcefully resized to the target dimensions (e.g., 800x600 or custom) and snapped to its grid position. Manually stretching the window with the mouse should trigger an auto-correction back to the grid.

* [ ] **Step 3.3: UI Input Debounce:** Go to the Settings tab and rapidly type `200` into the custom resolution text box.
  * *Expected Result:* The system must wait until you finish typing before applying the configuration. If typing the number `2` immediately shrinks active windows to 64px (min size), the debounce logic is failing.

## FLOW 4: Process Management & Session Tracker Verification

**Goal:** Verify the background loop tracking stability (Preventing the "zombie respawn" issue).

* [ ] **Step 4.1: Graceful Kill (Manual Stop):** While an account is running in-game, click the `Kill / Stop` button for that specific account on the tool's UI.
  * *Expected Result:* The process terminates immediately. The Auto-Rejoin feature **MUST NOT** activate. The account status gracefully returns to Offline.

* [ ] **Step 4.2: Unexpected Crash (Auto-Rejoin Trigger):** Launch an account. Open Windows Task Manager, locate the corresponding `RobloxPlayerBeta.exe`, and click `End Task` (simulating a crash).
  * *Expected Result:* `SessionTracker` detects the unexpected exit. The UI status changes to "Rejoining..." and the countdown timer begins based on the configured auto-rejoin delay.

* [ ] **Step 4.3: Headless Process Protection:** Launch a new account. Observe the system during the first 5 seconds when the process exists but the main window hasn't appeared yet (`HWND == 0`).
  * *Expected Result:* The `KillHeadlessRobloxProcesses` cleanup routine must ignore this starting process. It is only permitted to kill headless processes if their uptime exceeds **45 seconds**.

**Final Assessment:**
If the system passes 100% of these checks—specifically **Step 2.2**—the asynchronous queue bug is officially patched, and the M38 architecture is robust and production-ready!
