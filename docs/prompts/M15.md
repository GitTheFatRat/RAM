## 1. VAULT FORMAT v2 AND MASTER PASSWORD (data-loss and downgrade protection)
1. Before the FIRST save that upgrades a v1 vault to v2, copy vault.dat to vault.dat.v1.bak. Never overwrite an existing v1 backup (if it exists, use a timestamped name). Test it.
2. The header (magic, version, kdfType, salt and every KDF parameter) must be authenticated: include all of it in the AES-GCM AAD. Store Argon2id parameters in the header so they can be raised later. Reject parameters below these minimums on load: memory 64 MiB, iterations 3, parallelism 1. Test: tampering with any header byte fails with VaultCorruptedException; parameters below minimum are rejected.
3. A wrong master password must never modify any file: test by hashing vault.dat and its .bak before and after a failed unlock.
4. Document the exact key construction (how the Argon2id output and DPAPI combine, and why every save still uses a fresh data key and nonce) in SECURITY.md in at most 15 lines. If the Argon2 package does not support net10.0 cleanly, mark BLOCKED, keep the vault on format v1, hide the master password toggle, and use PBKDF2-HMAC-SHA512 with at least 600000 iterations only if you can do it within the existing format design; otherwise stop this sub-feature.
5. Enabling the master password: a required confirmation checkbox with a localized warning that a forgotten password makes the vault unrecoverable, plus an offer to export an encrypted backup first. Minimum 12 characters (already specified). No password hints, no stored password, buffers zeroed after use.
6. Report the Argon2 package name and version.

## 2. PROXY SCOPE AND SAFETY
1. Proxy credentials are stored only inside the encrypted vault. Never log the proxy host, port, username or password (counts and booleans only).
2. The proxy applies to this tool's own HTTP requests (validation, ticket, presence-like calls) and, after M14.4, to the WebView2 login window using the proxy supplied in the login panel; the same proxy is stored on the new account. The Roblox game client launched through the roblox-player protocol connects directly and does NOT use the proxy. State this in the Proxy tab (localized note), in README.vi.md and in SECURITY.md. Do not claim the account's game traffic is proxied, and do not claim a proxy prevents bans or specific Roblox errors.
3. The host guard still applies to the request host (not the proxy). TLS is end to end, so the proxy cannot read the cookie; note it in SECURITY.md.
4. Tests: proxy settings reach the primary handler; invalid host or port is rejected; the proxy password never appears in logs or diagnostics (realistic-shaped fake values).

## 3. RISKY WINDOW AND PROCESS FEATURES (M10 throttle, M11 RAM cleaner)
These touch Roblox processes from outside. I cannot confirm how the Roblox anti-cheat treats them, so treat them like multi-instance.
1. Default OFF for both. Enabling either requires the same risk acknowledgment dialog as multi-instance (localized): it states that the feature acts on Roblox processes and may be treated as abnormal behavior; the user accepts at their own risk. Persist a separate acknowledgment flag per feature.
2. Scope: act ONLY on PIDs tracked by SessionTracker (sessions bound to an account), never on every RobloxPlayerBeta process. Skip the process that owns the foreground window.
3. Window throttle: minimize only (ShowWindow with a minimize-no-activate flag). Remove any "move off-screen" behavior. Never send input or synthetic messages to the windows.
4. RAM cleaner: keep handle rights minimal (only what SetProcessWorkingSetSize needs), close handles in finally, and record counts of trimmed, access-denied and failed processes. If every attempt in a cycle is access-denied for 3 cycles in a row, disable the feature, show a localized snackbar, and note it in Diagnostics.
5. Diagnostics report: add a line for each feature (enabled, acknowledged, last cycle counts). No PIDs of non-tracked processes.
6. Mark both UNVERIFIED-LIVE in docs/api-notes.md. Tests with fakes for process provider, native calls abstracted behind an interface.

## 4. GHOST DISCONNECT DETECTOR (M13) SAFEGUARDS
Risk: a wrong match kills a healthy session, and mapping a PID to a log file by creation time is fragile when several clients start close together.
1. Replace the boolean setting with a mode: Off, NotifyOnly, KillAndRejoin. Default NotifyOnly (the user sees an event on the Running page and a snackbar but nothing is killed). Migrate the old boolean: true maps to NotifyOnly.
2. Mapping must be unambiguous: bind a log file to a session only when exactly one unassigned log file was created within a configurable window (default 20 s) around the process start and no other session is a candidate for it. If ambiguous, do not monitor that session and log a warning (counts only). Never kill based on a log that is not bound to that exact PID.
3. Keywords: remove the bare "DisconnectReason" keyword. Keep "Connection lost", "Error 277", "Error 268" (case-insensitive). Make the keyword list editable in settings.json (Advanced) with the same validation style as launch templates (non-empty strings, at most 20 entries, each 3 to 80 characters).
4. Guards before any kill: session age at least 60 s; at most one kill per session per 5 minutes; the matched line must be newer than the session start. In NotifyOnly mode never kill.
5. The log watcher opens files with FileShare.ReadWrite, reads only appended text, never keeps a lock after the session ends, and never copies log content into the app logs or diagnostics except the keyword that matched.
6. Tests with temp log files and a fake clock: ambiguous mapping is not monitored; NotifyOnly never kills; KillAndRejoin kills only the bound PID after the guards; cooldown works; keyword editing validated.
7. docs/api-notes.md: log format and keywords are UNVERIFIED-LIVE. Add a MANUAL_TEST_CHECKLIST step: run in NotifyOnly for a few sessions, record whether any false positives occur before using KillAndRejoin.

## 5. LAUNCH PRECHECK (M14.2 is not robust)
Finding: a registry pre-check can still fail for installs that do not register the protocol under those three hives (for example a Microsoft Store install), and then blocks a launch that would have worked.
1. Remove the registry pre-check as a launch blocker. Launch by starting the roblox-player URI with the shell. If Windows reports that no application is associated (Win32Exception with NativeErrorCode 1155, or the shell's no-association code), return the localized "Roblox not installed or protocol not registered" error. Any other failure maps to a generic launch error code.
2. Keep the registry lookup (HKCU, HKLM, HKCR, with exception handling as in M14.2) only as information in Diagnostics: which hives contain the handler, the handler path with the Windows user name masked.
3. Diagnostics also lists the count of running processes named RobloxPlayerBeta and a note if a process named Windows10Universal is present (a hint that the Microsoft Store client is in use, which this tool does not track).
4. Update tests: fake process starter throwing the no-association error, success path, other error path.

## 6. UI DEFECTS FOUND IN SCREENSHOTS
1. Accounts grid shows a phantom white row at the top with an empty alias and a "not checked" chip. Most likely cause: DataGrid CanUserAddRows is true. Set CanUserAddRows false and CanUserDeleteRows false on every DataGrid in the app. Then verify no empty-alias account exists in the data path (the vault validator already rejects it) and report the finding.
2. Empty-state hint texts are wired to wrong resource keys: the Servers page shows the account search placeholder, the Running page shows the Settings "Launching" subtitle. Create dedicated keys (Servers_EmptyHint, Running_EmptyHint, and an error variant for a failed request) in both resx files and bind them. Distinguish "request failed" (show the error and a Retry button) from "no public servers" on the Servers page.
3. Page titles and secondary text look dim on the dark background. Use the primary text brush for page titles and the secondary text brush for descriptions, and add a test that computes the WCAG contrast ratio for each text/background token pair in both themes and requires at least 4.5:1 for body text and 3:1 for large titles.
4. Truncated column headers (for example "Thoi gian ch..." on the Running page): give columns sensible MinWidth or star widths, enable text trimming with a tooltip on headers.
5. The search box on the Accounts page is much taller than needed: remove the extra height.
6. Keep the M14.3 row and header styling; do not hard-code hex colors outside Themes/Tokens.xaml (the existing XAML scan test still applies). If M14.3 introduced hex colors in page XAML, move them to tokens.
