## 1. MULTI-INSTANCE REAL GATE (replaces the BLOCKED state from M4)
Several independent public open-source tools document that the Roblox client enforces a single instance through named kernel objects: a mutex named ROBLOX_singletonMutex and, in some descriptions, an event named ROBLOX_singletonEvent. The community tools work by creating these objects first, inside their own process. Public notes also warn that Roblox is actively blocking such tools, so success is NOT guaranteed and cannot be confirmed without a live Roblox client. Treat the names as UNVERIFIED-LIVE.

Implement in the existing NamedMutexInstanceGate / IInstanceGate (keep the interface, do not rename public contracts):
1. Constants for the two names ("ROBLOX_singletonMutex" as Mutex, "ROBLOX_singletonEvent" as EventWaitHandle) in ONE place. The names are injectable so tests use unique test-only names (for example "RbxManagerTest_" + Guid), never the Roblox names.
2. TryEnable: refuse with a localized message if any Roblox process is running (existing IProcessProvider check). Otherwise create BOTH objects in this application's own process and keep them for as long as the gate is enabled. If an object already exists (createdNew false), release anything already created, do not hold a partial state, and return a localized "could not take over; close Roblox and retry" error.
3. Mutex thread affinity: a Mutex must be released by the thread that owns it. Create and release the objects on one dedicated long-lived background thread controlled by a ManualResetEventSlim, so Disable and Dispose work from any thread. Dispose must be idempotent and must run at application exit.
4. IsAvailable becomes true in the production build. The settings toggle, risk warning dialog, acknowledgement persistence and default OFF behavior from M4 stay unchanged.
5. Boundaries (unchanged): own process only. No touching, patching, injecting into, hooking, or duplicating or closing handles in any Roblox process or memory.
6. Tests with test-only names: enable creates both objects (a second probe opening the same test name sees them); disable releases them (probe can create them afresh); dispose twice is safe; enable refuses when the process provider reports Roblox running; partial-creation failure leaves no held object.
7. docs/api-notes.md: add "ROBLOX_singletonMutex / ROBLOX_singletonEvent: UNVERIFIED-LIVE, public community sources only, Roblox may block". Update STATE.md (remove the BLOCKED item), SECURITY.md (what the gate does and does not do), and add a multi-instance step to docs/MANUAL_TEST_CHECKLIST.md: with two THROWAWAY accounts, enable the toggle with Roblox closed, launch account A, then account B; record whether the second client stays alive.
8. If the second client does not stay alive in the human test, the human will report it; do not add workarounds that touch Roblox processes.
