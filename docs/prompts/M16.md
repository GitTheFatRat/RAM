# M16: UI "eyes" for the agent (sandboxed UI automation, window-only screenshots)

Follow docs/prompts/RUNBOOK.md (rules, gates, token budget, security, autonomy). First add M16 to docs/STATE.md as pending. Batch file writes; do not narrate. Run only after M15 is done.

## PURPOSE
Let the agent run the real WPF app, drive it, and SEE it, without giving any tool control of the whole desktop. The agent gets (a) window-only PNG screenshots and (b) JSON dumps of the UI Automation tree, produced by an automated test harness that runs the app in an isolated sandbox with fake data. No desktop-control MCP server is required or allowed for this.

## SAFETY RULES FOR THIS MILESTONE (non-negotiable)
1. The harness only attaches to the app process it launched itself. It never captures the full screen, never touches other windows or processes, never sends input outside that window.
2. The app under test runs with a throwaway data directory, fake accounts with realistic-shaped fake cookies, and NO network and NO real Roblox launch. It must be impossible to touch the real vault, settings, logs or a real Roblox client.
3. All test-only behavior is compiled only into Debug builds (#if DEBUG). A Release build must ignore the environment variables below. Add a test that proves the Release configuration contains no UI-test hook (for example by scanning the Release assembly for the hook type names or by a compile-time constant exposed in a diagnostic).
4. Screenshots and dumps contain fake data only. They go to artifacts/ui/ (already ignored by git). Never commit them.
5. The Reveal() allowlist must NOT grow.

## 1. APP SIDE (Debug builds only)
1. Environment variable RBXMANAGER_DATA_DIR: when set (Debug only), every location currently under %LOCALAPPDATA%\RbxManager (vault, settings, places, logs, UI state, login temp folders if practical) resolves under that directory. When unset, behavior is unchanged.
2. Environment variable RBXMANAGER_UITEST=1 (Debug only):
   - Replace the real network and launch services with offline fakes through DI: auth/validation returns canned results, server browser returns canned pages including an empty page and a failing page (selectable through a fixed fake place id), launcher pretends to succeed without starting any process, process provider returns a fixed fake list of sessions.
   - Seed the data directory with fake accounts (varied statuses, groups, long aliases and usernames, one Expired) through the normal vault code and a fake DPAPI-safe path.
   - Use a different application single-instance mutex name so a real running copy of the app does not interfere.
   - Refuse to start (log and exit) if RBXMANAGER_DATA_DIR is unset or resolves inside the real %LOCALAPPDATA%\RbxManager.
3. Give every interactive control a stable AutomationProperties.AutomationId and every icon-only control an AutomationProperties.Name. Add a test that scans the XAML for icon-only buttons without a Name.

## 2. HARNESS (tests/App.UiTests, net10.0-windows)
1. Test category "UI". Excluded from the default `dotnet test` (needs an interactive desktop and the Debug build). Provide tools/run-ui-tests.ps1 that builds the Debug configuration and runs `dotnet test --filter Category=UI`.
2. UI automation library: prefer FlaUI (FlaUI.Core and FlaUI.UIA3). Verify net10.0-windows compatibility first and record the version. If it is not compatible or is unmaintained, use the built-in System.Windows.Automation client instead; do not add an unvetted package.
3. Each run: create a unique temp data directory, launch the Debug app executable with the two environment variables, wait for the main window, run the scenarios, always kill the process and delete the temp directory in a finally block.
4. Window-only capture: capture the app window with the Win32 PrintWindow API using the render-full-content flag (verify the flag in the Microsoft documentation), so windows on top of the app never appear in the image. Never use a full-screen capture. Save PNGs as artifacts/ui/<run-timestamp>/<scenario>-<theme>.png.
5. UI tree dump: for each captured screen write <scenario>.uia.json with, per element: ControlType, AutomationId, Name, IsEnabled, IsOffscreen and BoundingRectangle. Skip any value of a password or text input (record only that it exists).
6. Scenarios, each in Dark and Light themes: every navigation page (Accounts, Servers, Running, Diagnostics, Settings); accounts with search, sort, group filter, context menu, add via cookie dialog with fake values, edit, delete confirmation; empty states (empty vault, no search results); servers page with canned list, empty page and failing page; running page with fake sessions; settings toggles including the risk acknowledgment dialog and theme switch; diagnostics run (offline fakes); launch dialog dry run; LoginWindow proxy panel (do not start the browser).
7. Automatic assertions:
   - No unhandled-exception dialog and the process stays alive through each scenario.
   - No interactive element with an empty Name and AutomationId.
   - In Dark theme, sample the screenshot pixels inside each DataGrid's bounding rectangle and fail if more than 2 percent of the pixels are near white (luminance above 0.85). This catches the white row regression.
   - No control reports a BoundingRectangle larger than its window.
   - Page titles and column headers are present and non-empty.
8. A summary file artifacts/ui/<run-timestamp>/summary.md listing scenarios, pass or fail, and the list of image paths.

## 3. AGENT WORKFLOW (document in docs/UI_TESTING.md, at most 40 lines)
After any milestone that changes XAML, themes or view models: run tools/run-ui-tests.ps1, open every generated PNG with the image viewing capability, list the visible defects in docs/reports/<milestone>.md (layout overflow, truncation, low contrast, misplaced elements, wrong text), and fix the obvious ones. If the agent cannot view images, rely on the UIA JSON and the automatic assertions and say so in the report.
The standing rules for this workflow live in PROJECT_CONTEXT.md in a "Standing agent rules" block maintained by the user. Verify the block exists and that its UI verification bullet matches this milestone (script name tools/run-ui-tests.ps1, output folder artifacts/ui/). If the block is missing, add a minimal one covering: documentation lookup through MCP when available, no desktop-control or browser-control MCP, the UI verification workflow, and never touching the real data directory or starting a real Roblox launch from an agent session.
