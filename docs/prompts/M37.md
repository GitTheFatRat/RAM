# M37 BUG FIX: Allow Draggable Auto-Tiled Windows (Decouple Position Lock from Size Lock)

## PROBLEM
The `WindowSizeLock` hook (listening to `EVENT_OBJECT_LOCATIONCHANGE`) is aggressively enforcing both Size (Width/Height) and Position (X/Y). When a user attempts to manually drag a tiled Roblox window, Roblox momentarily forces its 800x600 minimum bounds, and the hook reacts by snapping the window back to its original grid position and 200x400 size. This makes the windows impossible to move manually.

## TASKS

1. **Decouple Placement from Locking:**
   - **Initial Placement:** The grid system (`RobloxWindowSizer` / `NextFreeSlot`) should apply the X/Y coordinates **only once** upon initial window creation or recreation.
   - **Continuous Lock:** The `WindowSizeLock` event handler (`OnWinEvent`) must **only enforce the size**, not the position.

2. **Apply `SWP_NOMOVE` in the Event Hook:**
   - Inside `WindowSizeLock.OnWinEvent`, when calculating the correction via `SetWindowPos` (or `User32.MoveResizeWindow`), explicitly add the `SWP_NOMOVE` (0x0002) flag.
   - This tells Windows: "Keep the window exactly at the X/Y coordinates where the user is currently dragging it, but force the Width and Height back to the target bounds (e.g., 200x400)."

3. **Ignore Position-Only Events (Optimization):**
   - In the hook, check if the window's current Width and Height already match the target. If they match, `return` early. Do not trigger `SetWindowPos` if the user is just dragging the window without the size changing. (This reduces the 800x600 flickering fight between Roblox and the hook).
