## 2. LAUNCH PACING
1. Settings: replace LaunchDelayMs with LaunchDelaySeconds. Default 20, minimum 1, maximum 600. The settings page shows seconds with a NumberBox. Localized description (Vietnamese with full diacritics and English): the spacing between two account launches; short spacing may be treated as unusual activity; the default is 20 seconds. Do not promise that any value prevents locks.
2. Migration (tolerant settings load): if settings.json has only the old LaunchDelayMs, then 3000 (the old default) means unset and gets the new default of 20 seconds; any other value is converted to seconds, rounded up and clamped. Test it.
3. Enforcement: one global gate in the launcher guarantees at least LaunchDelaySeconds between the starts of two launches. It must cover EVERY path: single launch, bulk launch and launch group, join from the Servers page, auto-rejoin, and smart server hopping. Add a test per path proving it goes through the same gate. The first launch after application start is not delayed. Dry runs are not launches and are not delayed.
4. Concurrent launch requests are serialized and spaced by the gate. Cancellation removes a waiting request without consuming the interval.
5. Bulk launch UI: show the queue and a countdown ("Next account in 14 s", localized), cancellable, per-account result list as today.
6. "Check all" (cookie validation) runs sequentially with a fixed 2 second gap between accounts instead of concurrency 3, cancellable, with the existing progress indicator.
7. Tests with a fake time provider: spacing is respected for consecutive launches from each path; settings clamping; migration; cancellation; Check all spacing.
